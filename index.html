The Promise and Reality of Chatting with Your Database

Imagine a world where business analysts can query complex enterprise databases using plain English. No SQL knowledge required. No waiting for data teams to write queries. Just natural conversation with your data.

This isn't science fiction — it's the promise of Natural Language to SQL (NL2SQL) systems powered by Large Language Models. But as I discovered while building a production-grade SQL agent for our enterprise data warehouse, there's a massive gap between a working prototype and a system you'd trust with business-critical decisions.

The Core Problem: LLMs are brilliant at understanding natural language and generating SQL syntax. But they know absolutely nothing about your specific database schema, business logic, or domain terminology.

This article chronicles our journey from a hallucination-prone prototype with 45% accuracy to a production system achieving 92% accuracy — not by swapping models or throwing more compute at the problem, but through database-side optimization techniques that most engineering teams overlook.

System Architecture: How It All Fits Together

Before diving into the problems and solutions, let's understand the architecture. Unlike typical RAG (Retrieval-Augmented Generation) systems that require vector databases and embedding pipelines, Oracle Select AI provides a tightly integrated approach where the database itself handles schema metadata injection.

The Data Flow (Step by Step)

  1. User Input: Business user types "Show me total headcount by department" in the APEX interface
  2. APEX Processing: PL/SQL function calls DBMS_CLOUD_AI.GENERATE() with the user's query
  3. Schema Injection: Select AI automatically injects table/column metadata from COMMENT ON statements
  4. Prompt Augmentation: System prompt + schema context + user query combined into enriched prompt
  5. LLM Processing: Cohere R+ generates SQL based on the comprehensive context
  6. Execution: Generated SQL is validated and executed against the database
  7. Results: Data returned to user in natural language or tabular format

Key Insight: The magic happens in step 3. By storing business semantics directly in database metadata, we eliminate the need for external vector stores and complex RAG pipelines. The database is the knowledge base.

Categorizing the Failures

After analyzing 200+ failed queries, we categorized them into four distinct failure modes:

Failure Type Frequency Example Root Cause
Column Hallucination 38% Invented employee_count column LLM guessed based on naming patterns
Table Misidentification 22% Queried contractors table (doesn't exist) Business term not mapped to schema
Incorrect Joins 25% Joined on wrong foreign keys No relationship metadata
Business Logic Errors 15% Didn't filter inactive employees No domain knowledge in schema

The Hard Truth: With 45% accuracy, our system was essentially a coin flip. No VP would approve rollout to 5,000 business users with those numbers. We needed a fundamental rethink.

The Solution: Teaching the Database to Speak AI

The breakthrough came from an unexpected realization: we were treating the database schema as a static artifact when it should be a dynamic knowledge repository.

Instead of trying to improve the LLM (which we couldn't control) or building complex external knowledge systems, we enriched the database itself with semantic metadata that Select AI could automatically inject into prompts.

Pillar 1: Schema Metadata Enrichment

This is the secret sauce. By adding comprehensive COMMENT ON statements to tables and columns, we give the LLM the business context it desperately needs.

Think of it as: Embedding business knowledge directly into your schema definition. When Select AI generates prompts, it automatically includes these comments as context.

Example: Table-Level Comments

COMMENT ON TABLE employees IS
'Comprehensive employee master list. Includes all full-time employees,
contractors, and interns as of current date. Use this table for headcount
analysis, org charts, and workforce reporting. The headcount column should
be used for aggregation (always 1 per active employee).';

Example: Column-Level Comments

COMMENT ON COLUMN employees.headcount IS
'Counting field for aggregation. Always set to 1 for active employees,
0 for inactive. SUM this column for total headcount calculations.
Alias: staff_count, employee_count, workforce_total.';

COMMENT ON COLUMN employees.employment_type IS
'Employment classification. Valid values: FULL_TIME (permanent employees),
CONTRACTOR (external consultants), INTERN (temporary interns).
Use for workforce composition analysis.';

COMMENT ON COLUMN employees.dept_id IS
'Foreign key to DEPARTMENTS table. Links employee to their assigned
department. Join to departments.dept_id to get department name and
budget information.';

Pillar 2: Synonym Mapping for Business Terminology

Business users don't think in database column names. They use domain-specific jargon. Synonyms bridge this lexical gap without requiring schema changes. 

-- Create views for employment type filtering
CREATE OR REPLACE VIEW contractors AS
    SELECT * FROM employees
    WHERE employment_type = 'CONTRACTOR' AND is_active = 'Y';

CREATE OR REPLACE VIEW full_timers AS
    SELECT * FROM employees
    WHERE employment_type = 'FULL_TIME' AND is_active = 'Y';

-- Department name variations
CREATE SYNONYM depts FOR departments;
CREATE SYNONYM orgs FOR departments;

-- Add comments to synonyms
COMMENT ON TABLE contractors IS
'View showing only contractor employees. Use for vendor management
and cost analysis. Excludes full-time and intern employees.';

Now when a user asks "show me all contractors," the LLM sees the synonym/view and understands it maps to employment_type = 'CONTRACTOR'.

Pillar 3: AI Profile Prompt Engineering

The AI profile configuration is where we set behavioral guardrails for the LLM. Critical parameters include: 

BEGIN
    DBMS_CLOUD_AI.CREATE_PROFILE(
        profile_name => 'GENAI_COHERE',
        attributes => JSON_OBJECT(
            'provider' VALUE 'oci',
            'oci_model_id' VALUE 'cohere.command-r-plus',

            -- CRITICAL: Set temperature to 0 for deterministic SQL
            'temperature' VALUE 0.0,
            'max_tokens' VALUE 600,

            -- Custom system prompt
            'conversation_context' VALUE '
You are a SQL expert for an Oracle Autonomous Database.

CRITICAL RULES:
1. ONLY use tables and columns that exist in schema metadata
2. NEVER invent column names - check comments for exact names
3. Always filter out inactive records (is_active = ''Y'')
4. Use headcount column for employee counting (SUM(headcount))
5. Return ONLY the SQL query without explanations
'
        )
    );
END;
/

Temperature = 0: This is non-negotiable for SQL generation. Any creativity in column names or table structures leads to hallucinations. We need deterministic, schema-compliant output.

Pillar 4: Index Optimization

Accurate SQL is useless if it takes 30 seconds to execute. We added targeted indexes for common query patterns: 

-- Indexes for common join patterns
CREATE INDEX idx_emp_dept ON employees(dept_id);
CREATE INDEX idx_emp_type ON employees(employment_type);
CREATE INDEX idx_emp_active ON employees(is_active);

-- Composite index for frequent filtering combination
CREATE INDEX idx_emp_dept_active ON employees(dept_id, is_active);

-- Date-based queries
CREATE INDEX idx_emp_hire_date ON employees(hire_date);

Implementation: The Frontend Integration

With the database optimized, we needed a user interface. Oracle APEX provided a low-code solution that integrates seamlessly with Select AI via PL/SQL.

APEX AJAX Callback Function

The integration is surprisingly simple — a single PL/SQL function that handles the entire request/response cycle: 

DECLARE
    v_user_question CLOB := APEX_APPLICATION.g_x01;
    v_ai_response   CLOB;
    v_profile_name  VARCHAR2(100) := 'GENAI_COHERE';
BEGIN
    -- Input validation
    IF v_user_question IS NULL THEN
        APEX_JSON.open_object;
        APEX_JSON.write('status', 'error');
        APEX_JSON.write('message', 'Please enter a question');
        APEX_JSON.close_object;
        RETURN;
    END IF;

    -- Call Select AI
    v_ai_response := DBMS_CLOUD_AI.GENERATE(
        prompt       => v_user_question,
        profile_name => v_profile_name,
        action       => 'chat'  -- Returns SQL only
    );

    -- Return JSON response
    APEX_JSON.open_object;
    APEX_JSON.write('status', 'success');
    APEX_JSON.write('sql', v_ai_response);
    APEX_JSON.close_object;

EXCEPTION
    WHEN OTHERS THEN
        APEX_JSON.open_object;
        APEX_JSON.write('status', 'error');
        APEX_JSON.write('message', SQLERRM);
        APEX_JSON.close_object;
END;

JavaScript Frontend (APEX Page)

function sendQuery() {
    const userQuery = apex.item('P1_USER_QUERY').getValue();

    apex.server.process(
        'GENERATE_SQL_FROM_NL',
        { x01: userQuery },
        {
            dataType: 'json',
            success: function(response) {
                if (response.status === 'success') {
                    apex.item('P1_GENERATED_SQL').setValue(response.sql);
                } else {
                    apex.message.showErrors([{
                        type: 'error',
                        message: response.message
                    }]);
                }
            }
        }
    );
}

Breaking down the 47-percentage-point improvement by optimization technique:

Key Takeaway: Column-level metadata had by far the highest ROI. If you only do one thing from this article, add comprehensive COMMENT ON COLUMN statements to your most-queried tables.

Conclusion: Metadata is the Real RAG

The conventional wisdom in AI engineering circles is that improving LLM accuracy requires:

  • Larger models with more parameters
  • Extensive fine-tuning on domain data
  • Complex RAG pipelines with vector databases
  • Prompt engineering black magic

Our experience building a production NL2SQL system tells a different story: the most impactful improvements come from structuring and enriching the data itself.

The Paradigm Shift: Instead of asking "how do we teach the AI about our database?" ask "how do we make our database self-describing to AI?"

Lessons Learned

  1. Schema metadata is underutilized infrastructure. Most teams treat COMMENT ON statements as optional documentation. In the age of LLMs, they're critical knowledge assets.
  2. Business terminology must be mapped at the database level. Synonyms and views are cheap to create and eliminate entire categories of hallucinations.
  3. Temperature = 0 is non-negotiable for SQL generation. Any creativity in schema references will cause failures.
  4. The 80/20 rule applies. Optimizing the 15 most-queried columns gave us 80% of the accuracy gains.
  5. Measure everything. Without rigorous A/B testing across 200+ queries, we wouldn't have known which optimizations actually worked.

Future Directions

We're now exploring:

  • Automated metadata generation: Using LLMs to draft initial COMMENT ON statements from existing data dictionaries
  • Query feedback loops: Learning from user corrections to improve schema descriptions
  • Multi-table reasoning: Expanding beyond single-join queries to complex analytical workloads
  • Role-based schema filtering: Different object lists in AI profiles based on user permissions
